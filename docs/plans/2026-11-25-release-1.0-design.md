# drift 1.0: public release — design
Status: approved · Date: 2026-11-25

## Problem

drift works (mirroring, Play on TV, popup, page remote; checked end to end on the Samsung), but only a developer can
install it: load the extension unpacked from a source build, sync the host with `uv`, register it with
`scripts/install-host.sh --extension-id <id>`. Nothing is versioned, packaged or published, the extension had no
icons, and nothing tells a user what to do when the host is missing.

## Goals / Non-goals

Goals
- **Anyone can install drift**: the extension from the Chrome Web Store; the host from a native installer for
  their OS (`.pkg` macOS, `.exe` Windows, `.deb`/`.rpm` Linux), or from PyPI for developers.
- **Version 1.0.0**, one version for extension and host, semantic versioning from here; a changelog.
- **A release workflow**: a `v*` tag builds everything, tests the installed packages, and drafts a GitHub Release
  with checksums; publishing to PyPI (trusted publishing) and, later, the Web Store.
- **Signing-ready**: unsigned at first, signing switched on by adding secrets.
- **The popup guides users**: a missing host shows a download card; an outdated one asks to update.
- **A security audit** of the code and everything packaging adds, findings fixed or recorded.
- **Documentation for users**: install guide per OS (including the unsigned-installer prompts), privacy, README
  with screenshots, store listing with screenshots and a promo tile.

Non-goals
- Edge Add-ons store (Edge installs from the Chrome Web Store; a separate listing would mean a second id).
- Auto-update of the host (users reinstall; the popup says when). The extension auto-updates from the store.
- Signing for 1.0 (prepared, not done), Linux packages other than `.deb`/`.rpm`, ARM Linux.
- FairPlay (skipped), the MacBook as a receiver (separate work).

## Constraints check

| Constraint | This design |
|---|---|
| **MV3** | No new permissions. Icons and a fixed `key` (dev builds only) in the manifest. The popup's download link opens a tab (`chrome.tabs.create`), no host permission needed. |
| **Untrusted input** | Unchanged message handling. New inputs: the host's reported version (validated by the protocol) and nothing else. |
| **LAN only, no cloud** | drift itself still talks to nothing outside the LAN. The popup links to the GitHub Releases page only when the user clicks Download. Fonts stay local. |
| **Cross-platform** | Installers for macOS (arm64; x86_64 if a runner exists), Windows x64, Linux x64; system-wide manifest paths per OS and browser, verified (step 2). |
| **Protocol** | No change: `hello` already carries the host version. |
| **Least privilege** | Installers register the host only for the Web Store extension id. macOS/Linux files root-owned, not writable by others; Windows per-user install, no admin. |
| **Dependencies** | Build-time only, in CI: PyInstaller, Inno Setup, nfpm (all free/OSS). No new runtime dependencies. |

## Chosen approach

Native installers wrapping a PyInstaller "one folder" build (fast start: the browser launches the host often), a
tag-driven GitHub Actions workflow that builds, installs and tests every package before drafting a release, and the
Chrome Web Store for the extension. Why not the alternatives: a self-registering download (less familiar to users);
PyPI only (needs Python); a single-file build (slow start on every launch); store auto-publish from day one (the
first upload has to be manual to get the id).

## Design

### Host builds and installers

| OS | Package | Installs to | Registers |
|---|---|---|---|
| macOS | `.pkg` (pkgbuild/productbuild) | `/Library/Application Support/drift/` | system-wide manifests per browser (postinstall runs `drift-host install --system`); `uninstall` script left in the folder |
| Windows | `.exe` (Inno Setup), per user, no admin | `%LOCALAPPDATA%\Programs\drift\` | `HKCU` keys per browser; uninstall from Installed apps |
| Linux | `.deb`, `.rpm` (nfpm) | `/opt/drift/` | manifests under `/etc/…` per browser (package scripts); removed with the package |

- `install.py` gains a **system mode** (system manifest locations per OS and browser) beside today's per-user mode;
  `drift-host install --system [--extension-id …]` defaults to the Web Store id, and `drift-host --version` exists.
- Pairing credentials stay per user, as today.

### Extension in the Chrome Web Store

- The user creates the developer account and does the **first upload by hand**; the store assigns the permanent id.
  That id becomes the default everywhere (installers, `drift-host install`), and dev builds get the store's public
  key as `key` so an unpacked build has the same id. The store zip is built without `key`.
- Listing: icons (done: "Holo frame", design skill), 1280×800 screenshots in the three themes, a 440×280 promo tile,
  descriptions, a single-purpose statement, a justification per permission, privacy answers ("collects nothing")
  and `docs/privacy.md`.

### The popup when the host is missing or outdated

- Missing (the native port fails): a card "drift needs its companion app" with **Download for macOS / Windows /
  Linux** (detected OS first), opening `https://github.com/Alex-Fix/drift/releases/latest`.
- Outdated (host major < extension major, from `hello`): "Update drift-host" with the same link. Decisions in
  `popup/model.ts`, tested.

### Versions and release workflow

- One version; `scripts/set-version.sh X.Y.Z` updates `manifest.json`, `package.json`, `pyproject.toml`,
  `drift_host.__version__`; a test keeps them equal. `CHANGELOG.md` (Keep a Changelog).
- `.github/workflows/release.yml` on `v*` tags: check tag = version and run CI → extension store zip → host
  builds + installers per OS → install and test each package on a fresh runner → `uv build` + PyPI trusted
  publishing → draft GitHub Release with every file, `SHA256SUMS` and build-provenance attestations, notes from the
  changelog. Signing steps run only when their secrets exist.
- PRs touching packaging run the build-and-install tests too (no publishing).

## Security

The audit is a step of its own (step 8): the whole codebase against the `security` skill's checklist, plus what
packaging adds:
- **Installers:** files root-owned and not group/world-writable on macOS/Linux (a writable host binary would let any
  local user run code in every browser session); manifests list only the store id; no `PATH` changes; uninstall
  removes everything it added.
- **Supply chain:** GitHub Actions pinned to commit SHAs; build tools pinned; `npm audit` and `pip-audit` in CI;
  release artifacts with SHA-256 checksums and provenance attestations; PyPI via trusted publishing (no stored
  token); signing secrets only in the release job's environment.
- **The popup's download link:** a fixed URL in the code, never built from host or page data.
- **Existing surfaces re-checked:** the page remote's message gate, stream URL handling (the TV fetching LAN
  addresses, documented), event-channel decoding limits, credentials file mode, logs free of URLs and titles.

Findings are fixed in the step or recorded with a reason in this doc.

## Documentation and screenshots

- `README.md` rewritten for users: what drift does, screenshots, install (store + installer per OS), first pairing,
  limits (DRM never, YouTube mirrored, FairPlay receivers not supported). Developer setup moves to `CONTRIBUTING.md`.
- `docs/install.md`: per OS, including the unsigned prompts (macOS "Open Anyway", Windows "More info → Run
  anyway"), and uninstalling. `docs/privacy.md`. `docs/release.md`: the release checklist. `docs/architecture.md`:
  a packaging section. Skills updated (`host`: system install; `design`: store assets).
- **Screenshots** rendered from the real build in headless Chrome with a stubbed `chrome` (design skill): popup in
  all three themes (send, streaming with stats, mirroring), the page remote over a video and docked; 1280×800 store
  shots, a 440×280 promo tile, README images in `docs/images/`. Plus one real photo-style shot of the TV is left to
  the user if wanted.

## Testing

- Unit: version consistency, system manifest plans per OS and browser, popup host-missing/outdated decisions.
- Package tests in CI (above): install, manifests/registry, a real native-messaging `hello` against the installed
  binary, uninstall leaves nothing.
- Manual (`docs/release.md`): install the draft release on the Mac, pair, stream, mirror, remote, then publish.

## Open questions

1. System-wide manifest locations for Brave and Vivaldi (and Chromium on macOS) aren't consistently documented:
   verify on real installs (step 2).
2. Is an Intel macOS runner still available? If not: Apple-Silicon-only `.pkg` for 1.0, or a universal build.
3. Does the Web Store accept a zip with `key`? Assumed no: the store zip is built without it.
